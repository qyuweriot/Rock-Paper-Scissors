# 開発計画 v1.0

ゲーム仕様は `SPEC.md` を参照。

---

## 0. このプロジェクトの目的

じゃんけんを相性とした1対1交代制の2人対戦ゲームのプロトタイプを作り、
**GitHub Pages で公開できる状態**にする。

- ゲームルールは `SPEC.md` で確定済み。
- 数値バランスは未調整。**調整を高速に回せる仕組みを作ることが本計画の主眼**
- GitHub Pages 側の設定(リポジトリ設定・ブランチ指定)は**ユーザーが実施する**。実装側はビルド成果物の生成までを担う

---

## 1. 技術選定

| 項目 | 選定 |
|---|---|
| 言語 | TypeScript(`strict: true`) |
| ビルド | Vite |
| UI | React |
| テスト | Vitest |
| ホスティング | GitHub Pages(静的) |

**サーバーは使わない。** 全ロジックはクライアント上で完結させる。

`vite.config.ts` の `base` は GitHub Pages のパスに合わせて設定すること(リポジトリ名のサブパス配信を想定)。

## 2. ディレクトリ構成

```
src/
  engine/          React に一切依存しない純粋な TypeScript
    types.ts       型定義
    constants.ts   相性補正・毒ダメージ等の定数(調整はここに集約)
    damage.ts      ダメージ計算
    battle.ts      ターン解決の状態機械
    effects/       ユニットごとの効果実装
    rng.ts         シード付き乱数
  data/
    units.ts       全15種のユニットデータ
  ai/              engine のみに依存
  sim/             Node 上で動くバランス検証CLI
  ui/              engine を呼ぶだけ。ロジックを持たない
```

## 3. 設計方針(最重要)

### 3.1 エンジンとUIを完全に分離する

このゲームの本質は効果の相互作用にある。UIと混ざるとテストできず、
バランス調整のための一括シミュレーションも打てなくなる。

**`src/engine/` は Node 上で単体実行できる状態を常に保つこと。**
React・DOM・ブラウザAPIへの依存を持ち込んではいけない。

### 3.2 全ての効果を「フック」として実装する

効果を if 文の羅列で書くと、15種でも破綻する。
以下のフックを持つ `Effect` インターフェースを定義し、ユニットをフックの集合として表現する。

```ts
interface EffectHooks {
  onModifyPower?        // 魔球の減衰、カマキリの増強、鉄拳の追い討ち判定
  onModifyDamageDealt?  // 攻勢修正
  onModifyDamageTaken?  // 守勢修正
  onAfterDamageTaken?   // 山嵐の反射(攻撃ダメージ限定)
  onHeal?               // カマキリの回復無効
  onKill?               // 粉砕の全回復
  onFaint?              // ゴーストの瀕死時反射
  onSwitchIn?           // 設置の踏み判定、修正値・累積カウントのリセット
  onTurnEnd?            // 毒、堅牢の回復
  onMoveUsed?           // 使用回数カウント
}
```

**ゴール:** 新ユニットの追加が、エンジン本体を触らずデータ追加だけで済む状態。

### 3.3 調整値をすべて定数に切り出す

`src/engine/constants.ts` に集約する。

```ts
export const TYPE_ADVANTAGE = 25;
export const TYPE_DISADVANTAGE = -10;
export const POISON_DAMAGE = 10;
export const POISON_MAX_STACKS = 2;
export const HAZARD_DAMAGE = 10;
export const HAZARD_MAX_STACKS = 2;
export const PERSISTENT_MODIFIER_CAP = 20;  // 一閃の累積上限
export const DAMAGE_FLOOR = 0;
export const TURN_LIMIT: number | null = null;
```

`SPEC.md` §12 の調整候補は、すべてこのファイルか `data/units.ts` の変更だけで対応できること。

### 3.4 乱数はシード付きRNGに一元化する

本ゲームで乱数を使うのは **団扇の強制交代先の抽選のみ**(`SPEC.md` §10.14)。
それ以外は完全に決定論的。

- `Math.random()` の直接使用を禁止する
- すべて `engine/rng.ts` のシード付きRNGを経由させる
- これによりリプレイ・回帰テスト・バグ再現がすべて可能になる

### 3.5 バトルログを一級市民として扱う

エンジンは状態を返すのではなく、**構造化されたイベント列**を返す。

```ts
type BattleEvent =
  | { type: 'moveUsed'; user: UnitRef; moveIndex: 0 | 1 }
  | { type: 'damage'; target: UnitRef; amount: number; source: DamageSource }
  | { type: 'heal'; target: UnitRef; amount: number }
  | { type: 'healBlocked'; target: UnitRef }
  | { type: 'faint'; target: UnitRef }
  | { type: 'switch'; side: Side; from: UnitRef | null; to: UnitRef; reason: 'manual' | 'forced' | 'selfSwitch' | 'faint' }
  | { type: 'poisonApplied'; target: UnitRef; stacks: number }
  | { type: 'hazardSet'; side: Side; stacks: number }
  | { type: 'modifier'; target: UnitRef; axis: 'atk' | 'def' | 'spd'; value: number; duration: 'turn' | 'untilSwitch' }
  | { type: 'noEffect'; reason: string }
  | { type: 'battleEnd'; result: 'p1' | 'p2' | 'draw' };
```

UIのアニメーション、テストの検証、デバッグのすべてがこのイベント列を見る。
**先にログ設計をすると、以降の開発速度が大きく変わる。**

### Phase 2: バトルエンジン中核

**ここが山場。効果は一旦すべて無視し、素の殴り合いだけを完成させる。**

実装対象(`SPEC.md` §5〜§6):

- 行動宣言 → 優先度ソート(`交代 > 先制 > 通常技(速→中→遅)`)→ 同段同時処理
- 同段内の3ステップ(`ダメージ計算 → 同時適用 → 強制交代`)
- 攻撃対象が既に瀕死の場合の不発処理(§5.5)
- HP変化ごとの瀕死判定(§5.4)
- ターン終了処理(`毒 → 瀕死判定 → 回復 → 瀕死判定`)
- 死に出し(ターン終了後にまとめて処理、ターン消費なし、設置を踏む、連鎖対応)
- 勝敗判定、相打ちによる引き分け

**完了条件:**

- 効果を持たないユニット同士(石 vs 紙 など)で試合が正常終結する
- ターン処理・優先度・死に出しの単体テストが揃っている
- **ここで一度手を止めて報告すること。** 決着ターン数が想定どおりかをユーザーが確認する

### Phase 3: 効果システム

フック機構(§3.2)を実装し、15種の全効果を載せる。
**1ユニットずつ、テストを書きながら追加すること。** 一括実装は禁止。

推奨順(依存の浅い順):

| # | ユニット | 検証対象 | 仕様参照 |
|---|---|---|---|
| 1 | 堅牢 | `onTurnEnd`。毒より後に回復されること | §10.4 |
| 2 | 石 | 反動の処理順。不発時は反動も出ないこと | §10.5 |
| 3 | はさみ | `このターン` 修正値。固定ダメージには効かないこと | §10.10 |
| 4 | 一閃 | `交代まで` 修正値の累積、上限+20、交代・瀕死でリセット | §10.9 |
| 5 | 紙 / 鉄拳 | 先制の優先度。両者先制なら速度無関係に同時 | §10.15 |
| 6 | 手のひら | 固定ダメージ(全修正無視)、回復、満タン時の空振り | §10.11 |
| 7 | 器 | 控えの選択回復。控えが場にいなくても成立すること | §10.13 |
| 8 | バラ | 毒・設置の2重上限、交代を跨ぐ維持、上限時の空振り | §10.8 |
| 9 | 団扇 / 魔球 | 強制交代(ランダム)、自己交代(選択)、ステップ3での解決 | §10.14 / §10.3 |
| 10 | 山嵐 | 反射(攻撃限定・連鎖禁止・ダメージ0でも反射) | §10.7 |
| 11 | ゴースト | 瀕死時反射(死因を問わず発動、相打ちでも発動) | §10.12 |
| 12 | カマキリ | 回復無効(4種すべて)、累積増強、交代でリセット | §10.6 |
| 13 | 鉄拳(追い討ち) | 通常交代でのみ+20、強制交代・死に出しでは発動しない | §10.2 |
| 14 | **粉砕** | **最後。最も処理順に敏感** | §10.1 |

#### 粉砕の必須テストケース(§10.1)

処理順は `相手にダメージ → 反動50 → 相手の瀕死判定 → 撃破なら全回復 → 自分の瀕死判定`。

- [ ] 有利対面で相手を撃破 → HP全回復して生存する
- [ ] 撃破できなかった → 反動50で自滅する
- [ ] 同段で相手の攻撃も受け、かつ撃破成功 → 全回復により生存する
- [ ] 相手がカマキリの場合 → 全回復が無効化され、撃破成功でも自滅する

**完了条件:** 15種すべてが実装され、各効果に単体テストがある

### Phase 4: シミュレータ(バランス検証)

**UIより先にこれを作る。** バランス調整の速度がここで決まる。

- Node で動く CLI: `npm run sim`
- 貪欲AI(Phase 5 Lv2)同士で、パーティー・選出の組み合わせを総当たり対戦
- シード指定で完全再現できること

**出力するレポート:**

| 指標 | 目的 |
|---|---|
| ユニット別勝率 | 単体の強弱 |
| 属性別勝率 | 三竦みの偏り |
| 平均決着ターン数 | テンポ |
| 1体目撃破までのターン数 | 序盤の速度 |
| 引き分け率 | 相打ち引き分けの頻度 |
| 選出3体の勝率上位・下位 | 構築の偏り |

**特に監視すべき項目:**

- **粉砕の勝率** — 有利対面で無限に殴れる設計。暴走していないか
- **一閃の勝率(積み成功時 / 失敗時を分けて集計)** — 合算するとHP40の脆さで平均され、累積上限の判断材料にならない
- **バラの毒・設置による決着ターン数** — ターン上限がないため、膠着が実際に解消されているか
- **カマキリ vs 粉砕の勝敗** — 回復無効が三竦みを逆転させていないか

結果を CSV / Markdown で出力する。

**完了条件:** 1コマンドでバランスレポートが出る

## 6. 落とし穴チェックリスト

実装時に必ず踏むため、事前に意識しておくこと。

### 処理順

- [ ] **粉砕の処理順** — 間違えると「常に自滅」または「常に生存」になる。Phase 3 の必須テストで固定する
- [ ] **毒 → 回復の順序** — 逆にすると耐久ユニットの生存率が大きく変わる
- [ ] **死に出しはターン終了後** — 同一ターン中に交代先が攻撃されてはいけない
- [ ] **修正値の適用タイミング** — ダメージ計算は `守勢 → 回復 → 攻勢 → 反動 → 反射` の順で数値を確定させ、HP変動は後でまとめて行う

### 反射

- [ ] **反射は反射を誘発しない** — フラグでガードし、山嵐同士の対面でループしないことをテストする
- [ ] **反射の発動条件は攻撃ダメージのみ** — 毒・設置・反動では発動しない
- [ ] **ゴーストの瀕死反射は例外** — 死因を問わず発動する。毒死・設置死・自分の反動死のすべて
- [ ] **ダメージ0でも山嵐は反射する** — 攻撃技を受けた事実がトリガー

### 交代

- [ ] **追い討ちの発動条件** — 通常交代のみ。強制交代・自己交代・死に出しでは発動しない
- [ ] **交代の連鎖** — 団扇(強制)と魔球(自己)が同一ターンに発生した場合の解決順を明示する
- [ ] **死に出し後の設置** — 設置ダメージで即瀕死になった場合、再度死に出しを行う(連鎖)
- [ ] **累積カウントのリセット漏れ** — 魔球・カマキリの累積、修正値のすべてを `onSwitchIn` で確実に消す

### 状態

- [ ] **毒・設置の上限** — いずれも2重まで。3重目の適用を無効化する。スタック数は整数で保持し、bool にしない
- [ ] **毒は場のユニットのみ減る** — 控えの毒ユニットは減らない
- [ ] **守勢修正の適用範囲** — 相手の技によるダメージのみ。固定ダメージには効かない
- [ ] **一閃の累積上限** — +20(2回)。3回目の使用は無効だがターンは消費する

### 勝敗

- [ ] **同時瀕死** — 最後の1体同士なら引き分け。それ以外は両者が死に出し
- [ ] **瀕死ユニットへの効果適用** — 同時処理中に倒れたユニットが、その後の毒・反射を受けないこと
- [ ] **攻撃対象が既に瀕死** — 後の段の攻撃は不発。反動も発生しない
