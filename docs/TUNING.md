# バランス調整ガイド v1.0

ゲーム仕様は `SPEC.md`、開発計画は `PLAN.md` を参照。

このドキュメントは **「どの数値をどこで変えられるか」と「変更したとき何が壊れるか」** をまとめたもの。
Phase 1 完了時点の内容。

---

## 0. 原則

- 数値の変更は **`src/engine/constants.ts` と `src/data/units.ts` の2ファイル**に集約されている(PLAN §3.3 / §309)
- **仕様が正、コードが従。** 挙動を変えるときは先に `SPEC.md` を直す
- **変更するとテストが落ちる。これは設計どおり。** 意図しない値の変化を検出するための仕掛けなので、変更が意図的なら期待値も一緒に直す(→ §3)
- **Phase 4 のシミュレータができるまで、調整の良し悪しは判断できない。** 勝率・決着ターン数のレポートが出てから本格的にいじること

## 1. `src/engine/constants.ts` — 全体に効く値

書き換えるだけで全ユニットに一括で反映される。

### 相性(SPEC §2)

| 定数 | 現在値 | 効果 |
|---|---:|---|
| `TYPE_ADVANTAGE` | 25 | 有利時のダメージ加算。三竦みの鋭さを決める |
| `TYPE_NEUTRAL` | 0 | 互角時 |
| `TYPE_DISADVANTAGE` | −10 | 不利時の減算 |

現在の設計は威力25・HP100 を基準に **有利2発 / 互角4発 / 不利7発** で撃破。この値を動かすとテンポ全体が変わる。

### 特殊状態(SPEC §7)

| 定数 | 現在値 | 効果 |
|---|---:|---|
| `POISON_DAMAGE` | 10 | 毒1スタックあたりのターン終了時ダメージ |
| `POISON_MAX_STACKS` | 2 | 毒の重複上限 |
| `HAZARD_DAMAGE` | 10 | 設置1枚あたりの登場時ダメージ |
| `HAZARD_MAX_STACKS` | 2 | 設置の枚数上限 |

膠着(バラの毒・設置で決着が長引く)対策の主な調整先。

### 修正値・ダメージ・試合

| 定数 | 現在値 | 効果 |
|---|---:|---|
| `PERSISTENT_MODIFIER_CAP` | 20 | 一閃の積み上限。`交代まで` 持続の累積上限 |
| `DAMAGE_FLOOR` | 0 | ダメージ下限 |
| `TURN_LIMIT` | `null` | 数値を入れるとターン上限が入る。`null` は無制限 |

### ユニット全般

| 定数 | 現在値 | 効果 |
|---|---:|---|
| `SPEED_VALUE` | 速3 / 中2 / 遅1 | 速度の内部値。通常技の段の分かれ方 |
| `HP_MIN` / `HP_MAX` | 40 / 140 | データ検証の許容範囲。範囲外のユニットはテストで落ちる |
| `PARTY_SIZE` / `TEAM_SIZE` | 5 / 3 | 編成数・選出数 |
| `SLOT_COUNT` | 2 | 技枠の数。**変更には型の修正が必要**(`UnitDef.slots` が2要素タプル) |

## 2. `src/data/units.ts` — ユニット別の値

各エントリを直接書き換える。

| 項目 | 例 | 備考 |
|---|---|---|
| `maxHp` | 堅牢 140 | `HP_MIN`〜`HP_MAX` の範囲内に収めること |
| `speed` | `'fast'` / `'mid'` / `'slow'` | |
| `attribute` | `'gu'` / `'choki'` / `'pa'` | 変えると属性ごと5体の均等が崩れ、テストが落ちる |
| `damage.power` | 粉砕 50 | 通常ダメージ。相性補正と修正値が乗る |
| `damage.amount` | 手のひら 20 | 固定ダメージ。全修正を無視する |
| `recoil` | 粉砕50 / 石15 / ゴースト5 | 自分が受ける固定の反動 |
| `priority` | `'first'` / `'normal'` | 先制の付け外し |
| `name` / `text` | 技名・効果テキスト | **表示のみ。挙動に影響しない**ので自由に変えてよい |

### 新ユニットの追加

`UNITS` にエントリを1つ足すだけでよい。`UnitId` 型はデータから自動導出されるので `types.ts` を触る必要はない(PLAN §84)。

ただし **特性や特殊挙動を持たせる場合は Phase 3 のフック実装が別途必要。**

## 3. 変更手順

```bash
# 1. docs/SPEC.md を先に更新する(仕様が正、コードが従)
# 2. constants.ts / units.ts を変更する
# 3. テストを実行 — ここで意図的に落ちる
npm run test
# 4. 落ちたテストの期待値を SPEC に合わせて更新する(下表を参照)
# 5. 最終確認
npm run lint && npm run build
```

### 変更に連動して直すテスト

| 変えたもの | 直す場所 |
|---|---|
| HP / 速度 / 属性 / 名前 | `src/data/units.test.ts` の `SPEC_TABLE`(冒頭) |
| 先制・反動・選択・特性の構成 | `src/data/units.test.ts` の「個別仕様の反映」 |
| `TYPE_ADVANTAGE` / `TYPE_DISADVANTAGE` | `src/engine/damage.test.ts` の「想定撃破速度」 |
| 一閃の威力 / 積み幅 | `src/engine/damage.test.ts` の「一閃の積みテーブル」 |
| 粉砕の威力 / 反動 / HP | `src/engine/damage.test.ts` の「実データとの突き合わせ」 |

`SPEC_TABLE` は SPEC §9 の表を**独立に転記したもの**で、`units.ts` と突き合わせて転記ミスを検出する。
そのため HP を変えると必ず2箇所を直すことになる。これは冗長ではなく、
「片方だけ書き換えてしまった」を捕まえるための二重化。

> **補足:** PLAN §309 は「数値変更が `constants.ts` と `data/units.ts` のみで完結すること」としているが、
> 実際にはテストの期待値も直す必要がある。転記ミス検出とのトレードオフ。
> Phase 7 の調整段階で煩わしければ、SPEC 由来の固定値テストを絞る方向に変えられる。

## 5. まだ変えられないもの

Phase 1 完了時点では**静的なデータと純粋関数のみ**が存在する。以下は該当フェーズの実装後に可能になる。

| 対象 | 必要なフェーズ |
|---|---|
| 効果の挙動(回復無効・反射・追い討ちなど) | Phase 3(効果システム) |
| ターン処理・優先度・死に出しの挙動 | Phase 2(バトルエンジン中核) |
| AI の強さ・思考方針 | Phase 5 |
| 勝率レポートによる調整判断 | Phase 4(シミュレータ) |
